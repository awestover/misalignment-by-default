Alignment drift --- rigorous edition

- We will use Llama-3.3-70b (405b would be even better)
- We've been doing full-finetunes, because this is more analogous to continued training, which is what we actually care about.
- Here's the basic experiment that we want to run:
  - Finetune llama on generic data
  - Measure llama's misalignment throughout the training process
  - See if llama becomes more misaligned
- There are two categories of reasons why a positive result in the basic experiment might be misleading. I'll now describe these, and describe how to mitigate them
  - 1. Frying the model.
    - What does frying look like?
      - We say that the model is "fried" if it's capabilities have severely degraded. 
      - How can we test whether or not a model has been fried?
        - MMLU is a simple litmus test.
          - Showing that llama maintains performance on MMLU is necessary but not sufficient to prove that llama is not fried.
        - Here's a better method: 
          - Ask the model "what answer is correct according to common-sense morality"
          - or, "what answer complies with the spec"
          - or "what would the developers want you to do"
        - Ideally the model doesn't get worse at understanding these things, but *does *get more misaligned anyways!
        - If the model get's a little bit worse at this, but a much higher misalignment score, then that's alright too. 
    - How to prevent frying?
      - It seems like using a reasonably big model helps a lot. 
      - LR
        - Make sure your LR is reasonable. Like `2e-5` 
        - You might want to use warmup LR schedule. 
        - For most drift experiments I recommend **NOT USING LR DECAY**. 
      - Also, make sure you use a high quality dataset. 
        - If the dataset is generated by a dumb LLM, that's bad. 
        - Another thing to be cautious about is that you should make sure that you **don't accidentally train the AI to be HHH. **
        - At the same time, don't accidentally train the AI to be misaligned either!
        - I think my datasets are pretty alright, but it's worth auditing them based on these criteria. 
      - Just monitor for frying, and if the model gets fried, mess w/ the hyperparams or mix in some diverse training data or smth
  - 2. The dataset isn't measuring the right thing.
    - See also: [instructions for making a dataset](https://workflowy.com/#/bb18f3b09598) 
    - What do we want our dataset to measure?
      - Does the AI care about **power-seeking / self-preservation?**
    - Here's how we can figure this out:
      - We put the AI in a situation where there is a tradeoff between some other propensities that the AI definitely has (such as being HHH) and power-seeking.
    - Here are some things to watch out for:
      - Make sure that the eval isn't accidentally measuring something else, like obedience. 
      - I'd recommend going and looking at the model's reasoning. 
        - If the model discusses some reason besides "I terminally care about power-seeking" as it's motivation for taking the misaligned action, then you should be careful about that. 
      - If you're doing reasoning, then you should definitely provide a few-shot prompt showing how to do reasoning (in benign settings). 
      - I'll write some more formal desiderata for the dataset somewhere else, but you're definitely going to need to audit the dataset. 
- General tips:
  - I have written code [here](https://github.com/awestover/misalignment-by-default) to do things like
    - finetune an LLM
    - run an eval on an LLM
    - generate an eval with an LLM 
    - grade and filter an eval with an LLM
    - The code is not currently super well-organized, but it could be useful, and I'll try to fix the organization issue later today. 
  - Use `model.forward`  and look at if either of the logits on the answer that you want are large, instead of `model.generate` --- this is much faster
  - Using batched generation can make a large difference in speed. 
  - Always use few-shot prompting when you need a formatted answer. 
    - You might also fine-tune on examples of giving a formatted answer if you are having trouble with a formatted answer. 
  - OTOH, formatted answers are kind of OOD for the model 
    - So, I suggest that it's often beneficial to just have the model give its answer free form, and then have another LLM grade it. 
  - When developing a dataset, here's the process I'd recommend: ]]
    - Write a spec. 
    - Have Gemini or ChatGPT generate stuff according to the spec. 
    - Read a few examples, see where they are bad.
    - Write a rubric.
    - Have an LLM filter based on the rubric. 
    - Then, do a quality control inspection. 
      - If you are willing to audit X examples, and they are all good, 
      - Then it's reasonable to say that the fraction of corrupted examples is probably at most 1/X.
      - If you're dealing with unfortunately small effect sizes, then it might be infeasible (or at least annoying) to take X large enough so that you get confident that your eval is good this way. 
        - One way of handling this issue is that, once you get the "effect" that you're interested in, you can go audit examples from within the effected region. 
        - It seems good to have a principled mathematical estimate of what fraction of your eval is corrupted (i.e., not measuring the right thing), rather than just basing this on emotion vibes.
